Container-demuxer rebuild — DTS re-enabled for mp4/ts/m2ts, plus TrueHD in ts/m2ts
==================================================================================

Source: LG webOS-25 GStreamer 1.24 monorepo (lgstreamer/gstreamer-webos-25).
Built reproducibly by build-demux.sh (debian:11-slim, arm-linux-gnueabi-gcc, meson).

Why a rebuild was needed
------------------------
LG ships isomp4/mpegtsdemux with the DTS caps paths compiled out. Building with
-Ddca=true recompiles those paths, but they are ALSO gated at runtime by a
GObject property `dts_support` that LG defaults to FALSE — so mp4/ts DTS still
fell out as untargetable audio/x-gst-fourcc-dtsc. The fix is a 2-line source
patch flipping that default to TRUE:

  gst-plugins-good/gst/isomp4/qtdemux.c        qtdemux->dts_support = FALSE -> TRUE
  gst-plugins-bad/gst/mpegtsdemux/tsdemux.c    demux->dts_support   = FALSE -> TRUE

(each file has exactly one such assignment; nothing else changed; no later code
re-sets it to FALSE.)

Why TrueHD in .ts/.m2ts also needed a patch
-------------------------------------------
Separately from DTS, LG wraps the BluRay TrueHD stream-type case in tsdemux.c in
`#if 0` and falls through to `goto done`, so stream_type 0x83
(ST_BD_AUDIO_AC3_TRUE_HD) was silently DROPPED — the pad was never exposed. What
actually decoded was the AC-3 compatibility substream carried on the SAME BD PID,
which is why TrueHD in .ts/.m2ts "played fine" while not being TrueHD at all.
LG's own comment gates it on "until we have ability to decode this codec"; this
payload ships avdec_truehd (ranked 310 by install.sh), so that holds now. The
patch un-#if-0s the case:

  gst-plugins-bad/gst/mpegtsdemux/tsdemux.c   case ST_BD_AUDIO_AC3_TRUE_HD:
                                              #if 0 ... #endif / goto done -> live

The `stream->target_pes_substream = 0x72` inside that case is load-bearing: it
selects the TrueHD PES substream instead of the embedded AC-3 core. build-demux.sh
fails the build if the patch does not land, if audio/x-true-hd or substream 0x72
are missing afterwards, or if the preprocessor is left unbalanced.

Only tsdemux changed: libgstisomp4.so rebuilt BYTE-IDENTICAL (same md5) to the
previous artifact, which also confirms the build is reproducible.

On-device validation (real LG C5, via the media registry)
---------------------------------------------------------
Real Blu-ray DTS-HD MA 5.1 in .ts  -> gst-discoverer reports "audio: DTS,
  6 channels (FL FR FC LFE RL RR), 48000 Hz, 32-bit" and decodes to non-silent
  S32LE PCM end-to-end (dtsdec).
mp4 (dtsc)                          -> decodes to PCM.
normal AAC mp4                      -> unaffected (no regression).
(A residual/XLL-only DTS-HD test m2ts with no decodable core stays silent — a
 content limitation; reference ffmpeg fails on it too. Demux/routing is correct.)

TrueHD-in-m2ts validation (real LG C5, 2026-08-19)
--------------------------------------------------
Verified in an ISOLATED GStreamer environment on the TV (private plugin dir with
the patched tsdemux + symlinks to the 146 other system plugins, private
GST_REGISTRY), so the live bind-mounts were never touched:

  A real BD m2ts carrying TrueHD 5.1 + 4x AC-3 (VC-1 video)
    BEFORE: gst-discoverer exposed ONLY "audio #2/#3/#4: AC-3" — TrueHD absent,
            and tsdemux advertised no TrueHD/MLP caps at all.
    AFTER : "audio #2: Dolby TrueHD, Channels: 6 (FL FR FC LFE SL SR)", and it
            decodes to audio/x-raw S32LE 48000 channels=6 channel-mask=0x0c0f.

  The channel-mask is the discriminator: TrueHD decodes with the SIDE pair
  (0x0c0f) while AC-3 on this content decodes with the REAR pair (0x003f), so
  0x0c0f is positive proof the TrueHD substream — not the AC-3 core — is what
  reached the decoder.

  Regressions re-checked in the same run, both unchanged at channels=6/0x003f:
    DTS-HD MA in .ts   (188-byte stride)
    DTS-HD MA in .m2ts (192-byte BDAV stride)

NOT covered: TrueHD in .mp4. qtdemux.c has no TrueHD/MLP codepath at all (no
`mlpa` fourcc handling), so that needs new code, not a gate flip — still
unsupported and documented as such.
