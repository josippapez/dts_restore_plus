Container-demuxer rebuild — DTS re-enabled for mp4/ts/m2ts (with the DTS-HD
extension in ts/m2ts), TrueHD in ts/m2ts, and Dolby Vision profile 7 in MKV
==================================================================================

Source: LG webOS-25 GStreamer 1.24 monorepo (lgstreamer/gstreamer-webos-25).
Built reproducibly by build-demux.sh (debian:11-slim, arm-linux-gnueabi-gcc, meson).

Why a rebuild was needed
------------------------
LG ships isomp4/mpegtsdemux with the DTS caps paths compiled out. Building with
-Ddca=true recompiles those paths, but they are ALSO gated at runtime by a
GObject property `dts_support` that LG defaults to FALSE — so mp4/ts DTS still
fell out as untargetable audio/x-gst-fourcc-dtsc. The fix is a 2-line source
patch flipping that default to TRUE:

  gst-plugins-good/gst/isomp4/qtdemux.c        qtdemux->dts_support = FALSE -> TRUE
  gst-plugins-bad/gst/mpegtsdemux/tsdemux.c    demux->dts_support   = FALSE -> TRUE

(each file has exactly one such assignment; nothing else changed; no later code
re-sets it to FALSE.)

Why TrueHD in .ts/.m2ts also needed a patch
-------------------------------------------
Separately from DTS, LG wraps the BluRay TrueHD stream-type case in tsdemux.c in
`#if 0` and falls through to `goto done`, so stream_type 0x83
(ST_BD_AUDIO_AC3_TRUE_HD) was silently DROPPED — the pad was never exposed. What
actually decoded was the AC-3 compatibility substream carried on the SAME BD PID,
which is why TrueHD in .ts/.m2ts "played fine" while not being TrueHD at all.
LG's own comment gates it on "until we have ability to decode this codec"; this
payload ships avdec_truehd (ranked 310 by install.sh), so that holds now. The
patch un-#if-0s the case:

  gst-plugins-bad/gst/mpegtsdemux/tsdemux.c   case ST_BD_AUDIO_AC3_TRUE_HD:
                                              #if 0 ... #endif / goto done -> live

The `stream->target_pes_substream = 0x72` inside that case is load-bearing: it
selects the TrueHD PES substream instead of the embedded AC-3 core. build-demux.sh
fails the build if the patch does not land, if audio/x-true-hd or substream 0x72
are missing afterwards, or if the preprocessor is left unbalanced.

Only tsdemux changed: libgstisomp4.so rebuilt BYTE-IDENTICAL (same md5) to the
previous artifact, which also confirms the build is reproducible.

Why libgstmatroska.so is now rebuilt too (Dolby Vision profile 7)
-----------------------------------------------------------------
LG's matroska-demux.c returns early for dv_profile == 7 ("Dolby Vision profile 7
is not supported, but can play as HDR10."), so UHD-BD P7 MKVs never got Dolby
Vision caps. Three changes:

  gst-plugins-good/gst/matroska/matroska-demux.c
    1. `if (dv_profile == 7) { ...HDR10...; return TRUE; } else if (dv_profile < 7)`
       -> `if (dv_profile <= 7)`: P7 needs a dvcC box and reaches "Set as Dolby
       Vision".
    2. BlockAdditionMapping: remember each mapping's BlockAddIDType and parse
       BlockAddIDExtraData as a DOVI config only for dvcC (1685480259) / dvvC
       (1685485123). UHD-BD P7 MKVs carry a second hvcE mapping (the EL's HEVC
       config); its bytes overwrote dv_profile with 16 and killed playback.
    3. `demux->dts_support = FALSE` -> TRUE, as in the other two demuxers. With
       it FALSE this build drops A_DTS tracks (no pad, silent DTS MKVs), where
       LG's stock binary re-tags them for dtsdec. Now emits audio/x-dts.

Built with -Dmatroska=enabled -Dbz2=enabled (libbz2-dev:armel). Debian's bz2
soname is libbz2.so.1.0 but the C5 only has libbz2.so.1 (-> libbz2.so.1.0.8), and
LG's stock libgstmatroska.so NEEDs libbz2.so.1, so build-demux.sh rewrites the
NEEDED entry with patchelf 0.19.1.0 and fails the build if it did not land.

A FEL title (P7_FEL GIJoe) showed a green tint on some plays, both with a
byte-patched stock libgstmatroska.so and with this build (same file, same
binary, normal colours on other plays), only once the TV had been up for hours
(load ~15, 436 MB swapped, audiod restarted). After a fresh reboot every P7 clip,
incl. FEL with DTS or TrueHD audio, had correct colours and sound.

Why tsdemux was rebuilt again (DTS-HD extension substream, webos25-2.43)
------------------------------------------------------------------------
For the BD DTS stream types tsdemux kept only PES substream 0x71 (the DTS core)
and dropped 0x72, the DTS-HD extension substream that carries XLL/XBR/X96. That
did not matter while dtsdec (libdca) decoded the core only. dtsdec now decodes
the extension (ffmpeg dca, see ../out/BUILD-REPORT.txt), so the filter is
removed and both substreams reach dtsdec, whose parser joins core + extension
back into one frame:

  gst-plugins-bad/gst/mpegtsdemux/tsdemux.c   caps = ...("audio/x-dts");
                                              stream->target_pes_substream = 0x71;  -> removed

build-demux.sh fails the build unless exactly one such line is removed and none
is left afterwards ("DTS-HD patch OK").

  libgstmpegtsdemux.so : md5 6261cdabb6cac0432283b6f51c4915f0
                         sha1 112565206a8a9b726c2faf4ef0ff2769c7b9a11a
                         (was 8a490733c61c7ad0bdb5c9cb78d3547e)
  libgstisomp4.so      : md5 ee47bee841f5baff9f34e2f6f9b01792  (rebuilt byte-identical)
  libgstmatroska.so    : md5 03b28878b5201ddf68e8f38e49bf0f92  (rebuilt byte-identical)

TrueHD-in-m2ts validation (real LG C5, 2026-08-19)
--------------------------------------------------
Verified in an ISOLATED GStreamer environment on the TV (private plugin dir with
the patched tsdemux + symlinks to the 146 other system plugins, private
GST_REGISTRY), so the live bind-mounts were never touched:

  A real BD m2ts carrying TrueHD 5.1 + 4x AC-3 (VC-1 video)
    BEFORE: gst-discoverer exposed ONLY "audio #2/#3/#4: AC-3" — TrueHD absent,
            and tsdemux advertised no TrueHD/MLP caps at all.
    AFTER : "audio #2: Dolby TrueHD, Channels: 6 (FL FR FC LFE SL SR)", and it
            decodes to audio/x-raw S32LE 48000 channels=6 channel-mask=0x0c0f.

  The channel-mask is the discriminator: TrueHD decodes with the SIDE pair
  (0x0c0f) while AC-3 on this content decodes with the REAR pair (0x003f), so
  0x0c0f is positive proof the TrueHD substream — not the AC-3 core — is what
  reached the decoder.

  Regressions re-checked in the same run, both unchanged at channels=6/0x003f:
    DTS-HD MA in .ts   (188-byte stride)
    DTS-HD MA in .m2ts (192-byte BDAV stride)

Dolby Vision profile 7 MKV validation (real LG C5, webOS 10.3.1, 2026-09-28)
-----------------------------------------------------------------------------
Installed with install.sh (bind + stock.fp libgstmatroska= + APPLIED=verified;
uninstall.sh restores the stock md5 540b5548b90971b4698400c0e255f68a), then
played in LG's Media Player:
  P7 MEL MKV, P7 FEL MKV -> Dolby Vision badge, correct colours (stock: HDR10)
  P8.1 MKV               -> Dolby Vision + Atmos
  P5 MKV                 -> Dolby Vision + Atmos
  TrueHD-5.1.mkv         -> sound
  DTS in the P7 FEL MKV  -> sound (silent before change 3)
The FEL residual layer is NOT decoded (one video decoder): DV comes from the base
layer + RPU, the same result as a P7 -> P8.1 conversion. MP4 P7 is still HDR10 --
qtdemux.c has the same gate, left unpatched because no MP4 P7 sample is verified.

NOT covered: TrueHD in .mp4. qtdemux.c has no TrueHD/MLP codepath at all (no
`mlpa` fourcc handling), so that needs new code, not a gate flip — still
unsupported and documented as such.
